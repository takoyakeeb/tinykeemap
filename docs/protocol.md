# tinykeemap 通信プロトコル仕様

- 状態: **Draft v1**(`proto=1`)
- 対象: ブラウザ(WebSerial)⇔ RP2040-Zero 搭載キーボード(takoyaki8 ほか takoyakeeb シリーズ)
- この文書を仕様の正とする。ファーム側・ツール側はこれに従って実装する。
- takoyaki8 のファーム 0.5.0 で、この文書の内容を実機で確認している。
- 古いファーム(0.4.x)は、`CFG`、`INFO` の新しい項目(`cfg`・`lname`・`saved`)、次・前のレイヤーの keycode に対応していない。ツールは、`INFO` に `cfg=1` がないときは、設定の機能を使わない(§3)。

## 1. 基本方針

- USBシリアル(CDC)上の **テキストプロトコル**。人間がターミナルから手で打って試せる。
- **1行1コマンド**。ホストは行末に `\n`(LF)だけを付けて送る。
- 受信側(デバイス・ホストとも)は、`\n` と `\r` のどちらも行末として扱い、**空の行は無視する**(空の行に対して応答しない)。`\r\n` で送られても、間にできる空の行が無視されるので問題ない。
- 文字は ASCII のみ。コマンド名は大文字、16進数の a-f は大文字小文字どちらも可。
- **リクエスト/レスポンス方式**。ホストは1つコマンドを送ったら、応答が返るまで次を送らない。
- デバイスは必ず1コマンドにつき1行で応答する(デバッグ行は数えない。下記)。
  - 成功: `OK` または `OK <データ>`
  - 失敗: `ERR <コード> [メッセージ]`
- 行頭が `# ` (シャープとスペース)の行は **デバッグ出力** であり、応答ではない。
  - デバイスは、開発用ビルドなどで、いつでもデバッグ行を出してよい(応答の行の前後・間を問わない)。通常のビルドでは出さない。
  - ホストは、行頭が `# ` の行を無視する(ログに表示するのはよい)。応答を待っているときも、デバッグ行を応答として扱わず、次の行を待つ。
  - `OK` と `ERR` の応答は、行頭が `# ` になることはない。
- キー数・レイヤー数などは機種ごとに違うため、ツールは最初に `INFO` で問い合わせて動作する(機種ごとの専用実装を持たない)。

## 2. 用語

| 用語 | 意味 |
|---|---|
| layer | レイヤー番号。0 始まり。総数は `INFO` の `layers` |
| index | キー位置の番号。0 始まり。総数は `INFO` の `keys` |
| keycode | 16bit のキーコード。`0x` 付き16進で表記する(例: `0x0004`) |

### index の並び

マトリクスの行優先順とする: `index = row * cols + col`

takoyaki8(2行×4列)の例:

```
Col0  Col1  Col2  Col3
  0     1     2     3    ← Row0
  4     5     6     7    ← Row1
```

### keycode

keycode は 16bit。QMK の現行の値(2022-11-26 以降、keycodes 0.0.1 以降)と同じ構成とする。
(2022-11-26 より前の QMK は、基本キー以外の値が違う。この仕様は現行の値に合わせる。)

| 範囲 | 種類 | 内容 |
|---|---|---|
| `0x0000` | KC_NO | 何もしない |
| `0x0001` | KC_TRANSPARENT | 有効な下のレイヤーの設定を使う |
| `0x0004`〜`0x00A4` | 基本キー | USB HID の Usage ID(キーボードページ)。例: `0x0004` = A、`0x0005` = B |
| `0x00E0`〜`0x00E7` | 修飾キー単体 | 下の表 |
| `0x0100`〜`0x1FFF` | 修飾キー付き | 下位 8bit = 基本キー(`0x0004`〜`0x00A4`)、bit8〜12 = 修飾キー |
| `0x5200`〜`0x521F` | TO(n) | n = 下位 5bit |
| `0x5220`〜`0x523F` | MO(n) | n = 下位 5bit |
| `0x5260`〜`0x527F` | TG(n) | n = 下位 5bit |
| `0x7E00` | 次のレイヤー | 下の「次・前のレイヤー」。takoyakeeb 独自 |
| `0x7E01` | 前のレイヤー | 同上 |

修飾キー単体(`0x00E0`〜`0x00E7`。USB HID の Usage ID と同じ):

| 値 | 名前 | 値 | 名前 |
|---|---|---|---|
| `0x00E0` | LCTL(左 Ctrl) | `0x00E4` | RCTL(右 Ctrl) |
| `0x00E1` | LSFT(左 Shift) | `0x00E5` | RSFT(右 Shift) |
| `0x00E2` | LALT(左 Alt) | `0x00E6` | RALT(右 Alt) |
| `0x00E3` | LGUI(左 GUI) | `0x00E7` | RGUI(右 GUI) |

修飾キー付きの bit(下位 8bit の基本キーと OR で組み合わせる):

| bit | 意味 |
|---|---|
| `0x0100` | Ctrl |
| `0x0200` | Shift |
| `0x0400` | Alt |
| `0x0800` | GUI |
| `0x1000` | 右側 |

- 複数の修飾キーは OR で組み合わせる。例: Shift+A = `0x0204`、Ctrl+Shift+A = `0x0304`。
- `0x1000` が立っているときは、立っている修飾キーはすべて右側として扱う(左右の混在はできない)。例: 右Ctrl+A = `0x1104`。
- 下位 8bit が基本キー(`0x0004`〜`0x00A4`)でない値(Hyper / Meh など、下位 8bit が `0x00` の値や、修飾キー単体 `0x00E0`〜`0x00E7` との組み合わせを含む)は、この版では未定義。
- 修飾キーのビット(`0x0100`〜`0x0800`)が1つも立っていない値(右側のビット `0x1000` だけが立っている `0x1004` など)も、この版では未定義。
- レイヤー番号 n が `INFO` の `layers` 以上の keycode(例: `layers=4` のときの MO(4))は未定義として扱い、`ERR BADARG` にする。
- 次・前のレイヤー(`0x7E00`・`0x7E01`)は、QMK の「キーボード専用」の範囲(`QK_KB`。`0x7E00`〜`0x7E3F`)の先頭の2つ(`QK_KB_0`・`QK_KB_1`)を使う。QMK の標準の機能とはぶつからない。
- 上の表にない値は、この版では未定義。`0x00A5`〜`0x00DF` は QMK 独自の範囲(システム・メディア・マウスなど)で、この版では未定義。DF / PDF / TT / OSL / LT / LM / MT など QMK にある他の種類も未定義。
- ファームは、対応した種類だけ受け付け、それ以外は `ERR BADARG` で拒否してよい(対応していない種類があってもよい)。ツールは、未対応の値も送ってよい(拒否されたことは `ERR BADARG` で分かる)。

## 3. コマンド

| コマンド | 説明 | 成功時の応答 |
|---|---|---|
| `INFO` | デバイス情報を取得 | `OK name=takoyaki8 proto=1 fw=0.5.0 keys=8 rows=2 cols=4 layers=4 cfg=1 lname=5 saved=1` |
| `GET <layer> <index>` | 1キーの keycode を読む | `OK 0x0004` |
| `SET <layer> <index> <keycode>` | 1キーを書き換える(**RAMのみ**) | `OK` |
| `DUMP <layer>` | 指定レイヤーの全キーを index 順に取得 | `OK 0x0004 0x0005 ...`(`keys` 個) |
| `CFG LIST` | 設定の名前の一覧(候補が決まっているものは、候補つき) | `OK lname0 lname1 ... led led_mode=layer\|press\|breathe\|off ...` |
| `CFG GET <名前>` | 設定の値を読む | `OK 80`(値が空のときは `OK` だけ) |
| `CFG SET <名前> [<値>]` | 設定を書き換える(**RAMのみ**)。値を省くと初期値に戻る | `OK` |
| `SAVE` | 現在のキーマップと設定を Flash に保存(変わったほうだけ書く) | `OK` |
| `LOAD` | 起動したときと同じ状態に戻す。キーマップと設定を Flash から読み直す(未保存の変更は破棄。TG / TO の状態も解除する。下記「レイヤーの動き」) | `OK` |
| `RESET` | 初期キーマップに戻す(キーマップだけ。設定は戻さない。RAMのみ。Flashは `SAVE` するまで変わらない。TG / TO の状態も解除する) | `OK` |

`CFG` は、`INFO` に `cfg=1` があるファームだけが対応する。`cfg` がないファームでは、`CFG` は `ERR BADCMD` になる。ツールは、`cfg=1` がなければ、設定の機能を使わない。

### INFO の応答

`OK` のあとに `キー=値` をスペース区切りで並べる。ツールは**知らないキーを無視する**(将来の項目追加に備える)。

| キー | 意味 |
|---|---|
| `name` | 機種名(例: `takoyaki8`) |
| `proto` | プロトコルバージョン(整数)。この文書は `1` |
| `fw` | ファームウェアのバージョン |
| `keys` | キー数(1レイヤーあたり) |
| `rows` / `cols` | マトリクスの行数/列数(表示用) |
| `layers` | レイヤー数 |
| `cfg` | 設定(`CFG` コマンド)に対応しているとき `1`。なければ、対応していない |
| `lname` | レイヤー名(設定の `lname<n>`)の最大の文字数。`cfg=1` のときだけある |
| `saved` | `1` = 電源を入れ直しても、キーマップも設定も、いまと同じ。`0` = 保存していない変更がある(下記) |

`saved` は、ファームが、`INFO` を受けるたびに、いまの RAM のキーマップと設定を、「起動時に使われるもの」と比べて決める。

- 「起動時に使われるもの」は、Flash の内容が有効ならそれ、無効(未保存・壊れている)なら初期値。
- キーマップと設定の、どちらかが違えば `0`。
- TG / TO で有効にしたレイヤーの状態は、比べない(保存しないものなので)。
- `SAVE` が成功したあと、`LOAD` が成功したあと、起動した直後は、`1`。
- Flash が空の新品でも、RAM が初期値のままなら `1`。
- `SAVE` が `ERR` を返したときは、`SAVE` した内容のうち書けなかったほうが残るので、`0` のままになることがある。

### エラーコード

| コード | 意味 |
|---|---|
| `BADCMD` | 不明なコマンド |
| `BADARG` | 引数の数・形式が不正、未定義の keycode、設定の名前が不明、設定の値が使えない |
| `RANGE` | layer または index が範囲外 |
| `FLASH` | Flash の読み書きに失敗 |

例: `ERR RANGE layer 4 out of range`

`ERR` のコードのあとのメッセージは人間向けの参考情報で、文言は保証しない。ホストはコード(`BADCMD` など)だけで判断する。メッセージの例:

- `BADARG`: `usage: SET <layer> <index> <keycode>`(使い方の表示)/ `undefined keycode` / `unknown name`(`CFG` の名前が不明)/ `bad value`(`CFG SET` の値が使えない)
- `FLASH`(キーマップ): `erase failed` / `write failed` / `verify failed` など
- `FLASH`(設定): `FLASH cfg ` のあとに、`erase failed` / `write failed` / `too large` / `verify failed: ...` など(設定の保存のときだけ、`cfg` が付く)

### 挙動のルール

- `SET` と `CFG SET` は、RAM上のキーマップと設定を書き換え、**即座に**反映される。電源を切ると元に戻る。
- 確定したいときだけ `SAVE` を送る。これにより Flash の書き換え回数を抑える。`SAVE` を繰り返し送る動作は作らない。
- `SAVE` は、キーマップと設定の、**変わったほうだけ**を Flash に書く(どちらも変わっていなければ、何も書かずに `OK`)。キーマップを先に書き、設定をあとに書く。キーマップだけ書けて、設定が失敗したときは、`ERR FLASH cfg ...` を返す(キーマップは保存済みになる)。
- `SAVE` は Flash の消去を伴うため、応答まで時間がかかる場合がある。ホストのタイムアウトは 2 秒以上にする。他のコマンドは 1 秒で十分。
- `SAVE` は消去を伴うため、その間 USB が短時間止まる場合がある。takoyaki8 の実機では、キーを押している間に `SAVE` しても問題は見られなかった。
- `LOAD` は、起動したときと同じ状態に戻す。Flash の内容が有効ならそれを、無効(まだ保存していない、壊れている)なら初期値を使う。**Flash が空でも `ERR` にしない**。キーマップと設定は、別々に判断する(片方が無効でも、もう片方は Flash の値を使う)。
- `RESET` は、キーマップだけを初期キーマップに戻す。**設定は戻さない**。設定を初期値に戻すときは、`CFG SET <名前>`(値なし)を、名前ごとに送る。
- 起動時、Flash の内容が有効ならそれを読み込み、無効なら初期値を使う(§5)。

### レイヤーの動き

- 有効なレイヤー = レイヤー0(常に有効)+ TG / TO で有効にしたもの + MO を押している間のもの + トライレイヤーで有効になったもの(下記)。
- キーを押した時点で、有効なレイヤーを番号の大きい方から順に見て、最初の透過でない keycode を使う。すべて透過なら KC_NO。
- キーを離すときは、押した時点の keycode で処理する(途中でレイヤーやキーマップが変わっても同じ)。
- MO(n): 押している間だけ n が有効になる。
- TG(n): 押すたびに n の有効・無効が切り替わる(離すときは何もしない)。
- TO(n): TG / TO で有効になっているレイヤーを n だけにする(押している間の MO はそのまま)。TO(0) で土台のレイヤーだけに戻れる。
- n = 0 は常に有効なので、MO(0) と TG(0) は何もしない。
- レイヤーの状態は保存しない。起動時は、レイヤー0だけが有効。
- `RESET` と `LOAD` は、TG / TO の状態を解除してレイヤー0だけに戻す(押している間の MO はそのまま)。
- 目安: MO / TG のキーは、移動先のレイヤーの同じ位置を透過にしておく(そうしないと、そのキーで元に戻せないことがある)。
- 目安: 戻れなくなったときは、USB を抜き差しするか、ツールから `RESET` / `LOAD` を送るか、`SET` で戻れるキー(`TO(0)` など)を割り当てる。

#### 次・前のレイヤー

- `0x7E00`(次)と `0x7E01`(前)は、押したときに1回だけ動く(離すときは何もしない)。PC には、何も送らない。
- 「土台のレイヤー」を、1つ進める(戻す)。土台のレイヤーは、TG / TO で有効にしたレイヤーのうち、番号が最大のもの。1つもなければ 0。押している間の MO は、数えない。
- 土台のレイヤーから、次(または前)の向きに1つずつ見て、最初に見つかった「使われている」レイヤー n へ、TO(n) と同じに移る。押している間の MO は、そのまま。
- 「使われている」= 透過でない keycode が、1つでもあるレイヤー。レイヤー0は、いつも使われているものとして扱い、飛ばさない。
- 最後のレイヤーの「次」は 0 に戻る。0 の「前」は、最後の(使われている)レイヤーに移る。
- 使われているのが L0 だけのときは、何も起きない。

#### トライレイヤー

- 設定 `tri0`(値は `a,b,c` の形。例: `1,2,3`)で決める。「レイヤー a と b が**両方**有効なら、レイヤー c も有効にする」。
- MO・TG・TO のどれで有効になっていても同じ。押す順番も問わない。判定は、キーを押した時点の有効なレイヤーで行う。
- 片方を離す(無効にする)と、c も無効に戻る。
- `tri0` が空のときは、無効(初期値)。
- 画面(OLED)と LED の表示は、「いちばん番号が大きい有効なレイヤー」を使う(c が有効なら、c)。

### 修飾キーの動き

- 修飾キー単体(`0x00E0`〜`0x00E7`)は、押している間、その修飾キーを押す。
- 修飾キー付き(`0x0100`〜`0x1FFF`)は、押している間、指定された修飾キーと基本キーを押す。押すときは修飾キー、基本キーの順。離すときは基本キー、修飾キーの順。
- 同じ修飾キーを複数のキーが押しているとき(例: 左 Shift を押したまま `Shift+A` のキーを押して、`Shift+A` のキーだけ離す)は、押しているキーがすべて離れるまで、その修飾キーは押したままにする。
- 修飾キーの状態はキーを押した時点の keycode で決まり、離すときは押したときの修飾キーを離す(途中でキーマップやレイヤーが変わっても同じ)。

## 4. 設定(CFG)

キー以外の設定(レイヤー名、LED、OLED など)を、名前と値で読み書きする。`INFO` に `cfg=1` があるファームが対応する。

### コマンドの使い方

- `CFG LIST`: ファームが知っている設定の名前を、空白で区切って返す。ツールは、これで、使える設定を知る。
  - 候補が決まっている名前は、`名前=候補|候補|…` の形で返す(例: `led_mode=layer|press|breathe|off`)。
  - ツールは、空白で分けて、最初の `=` で、名前と候補に分ける。`=` がない名前は、自由な値(候補なし)。
  - 候補を `|` で区切るのは、`tri0` の値にカンマが出るため。
  - 候補は「画面に出す選択肢」。ファームは、候補にない名前も受け付けることがある(`led_mode` の項を参照)。
- `CFG GET <名前>`: 値を返す。値が空のときは、`OK` だけを返す。名前が不明なら `ERR BADARG unknown name`。
- `CFG SET <名前> [<値>]`: RAM の値を書き換える(すぐ反映。Flash には書かない)。確定は `SAVE`。
  - **値を省く(`CFG SET <名前>`)と、その名前の初期値に戻る**。
  - 名前が不明なら `ERR BADARG unknown name`。値がその名前で使えないときは `ERR BADARG bad value`(このとき、値は変わらない)。
- 値には、空白を入れられない。名前は小文字(`lname0` など)で、大文字小文字を区別する。
- 上の3つ以外の使い方(引数の数が違うなど)は、`ERR BADARG usage: ...`。

### 設定の名前

takoyaki8 の例。`lname` と `lcolor` の番号は、`0` 〜 `layers-1`。初期値は、機種(ファーム)ごとに決まる。

| 名前 | 意味 | 値 | 初期値(takoyaki8) |
|---|---|---|---|
| `lname0`〜 | レイヤー名(OLED に出す) | 英大文字・数字・`-`・`_`。`INFO` の `lname` 文字まで | L0 = `MAC`、L1 = `EDIT`、それ以外は空 |
| `led` | LED の明るさ | 0〜100(%) | `80` |
| `led_mode` | LED の効果 | `layer` / `press` / `breathe` / `off` | `layer` |
| `lcolor0`〜 | レイヤーごとの LED の色 | 6桁の16進(RRGGBB) | L0 = `2060FF`、L1 = `FF8000`、L2 = `20FF40`、L3 = `FF2080` |
| `oled` | OLED の明るさ | 0〜100(%) | `100` |
| `rotate` | OLED の向き | `0` / `90` / `180` / `270` | `0` |
| `tri0` | トライレイヤー(§3) | 空(無効)、または `a,b,c`(レイヤー番号3つ。それぞれ 1 以上、`layers` 未満) | 空 |

値の決まり(ファームが検査する。使えない値は `ERR BADARG bad value`):

- レイヤー名: 英大文字(A-Z)・数字・`-`・`_` だけ。スペースなし。小文字は使えない(ツールは、大文字にして送る)。最大の文字数は `INFO` の `lname`(takoyaki8 は 5。縦置きの OLED に収まる数)。空の名前は、OLED に名前を出さない。
- 割合(`led`・`oled`): 0〜100 の整数。先頭の 0(`007`)は、`7` にそろえて保存する。
- 効果の名前(`led_mode`): 英小文字・数字・`_` で、1〜12文字。
- 色(`lcolor`): 6桁の16進。a-f は大文字小文字どちらも可。保存するときは、大文字にそろえる。
- 向き(`rotate`): `0` / `90` / `180` / `270`。ボードを、USB-C が上の状態から、**時計回りに何度回して置くか**。`0` は、USB-C が上(いままでの向き)。90 と 270 は、横長の画面になる。
- トライレイヤー(`tri0`): 空、または `a,b,c`。

### LED と OLED

- OLED は、いまのレイヤー(いちばん番号が大きい有効なレイヤー)の番号と、その名前(`lname<n>`)を出す。`oled` は、明るさ(%)。
- LED は、キーの下の LED(takoyaki8 は4個)。色は、いまのレイヤーの `lcolor<n>`。
- `led` の 100% は、「安全な上限」(全部の LED を白で点灯しても、熱くならず、ちらつかない値)で、ファームが決める。
- `led` は、見た目が比例するよう、ファームが補正する。takoyaki8 は2乗(LED に送る値 = `255 × led² ÷ 10000`。1% 以上は、最低 1)。このため、`led` の 1〜8% は、LED に送る値が 1 で、見た目の差がない(10% 前後から上が、使える明るさ)。
- 効果の名前(`led_mode`):
  - `layer`: 全部の LED を、いまのレイヤーの色で点灯する(初期値)。
  - `press`: キーを押すと、全部の LED が光って、少しして消える。
  - `breathe`: レイヤーの色で、ゆっくり明るさが変わる。
  - `off`: 消灯する。
  - `test`: 診断用。画面には出さない(`CFG LIST` の候補にも入れない)。
  - **ファームが知らない名前は、`layer` と同じ動き**になる(`CFG SET led_mode` は、候補にない名前も受け付ける)。
- 効果の細かい設定(速さなど)は、将来、名前を足して決める(例: `led_speed`)。

### 知らない名前

- ファームは、`CFG LIST` にない名前(新しいファームで足された設定など)が、Flash に保存されていても、読み飛ばさずに持ち、`SAVE` のときも、そのまま書き戻す(ファームを入れ替えても、設定が消えない)。
- ただし、そのような名前は、`CFG GET` / `CFG SET` では使えない(`ERR BADARG unknown name`)。

## 5. Flash 保存形式

キーマップと設定は、それぞれ専用の 1 セクタ(4KB)に書く。別々のセクタで、`SAVE` では、変わったほうだけを書く。takoyaki8 では、Flash の使ってよい領域の、最後の1セクタがキーマップ、その1つ前のセクタが設定。

### キーマップ(マジック `TKM1`)

数値はすべてリトルエンディアン。

| オフセット | サイズ | 内容 |
|---|---|---|
| 0 | 4 | マジック `"TKM1"` |
| 4 | 1 | フォーマットバージョン(現在 `1`) |
| 5 | 1 | レイヤー数 |
| 6 | 2 | キー数(1レイヤーあたり) |
| 8 | 2 × layers × keys | keycode 配列(レイヤー順、各レイヤー内は index 順) |
| 末尾 | 4 | 上記すべて(マジックから keycode 配列まで)の CRC32(下記) |

CRC32 は標準的な CRC-32(zlib・ISO-HDLC と同じ。Go の `hash/crc32` の `ChecksumIEEE`)。多項式 0x04C11DB7(ビット反転表記で 0xEDB88320)、初期値 0xFFFFFFFF、入出力ともビット反転、最終 XOR 0xFFFFFFFF。対象はマジックから keycode 配列まで。値はリトルエンディアンで末尾に置く。確認用: ASCII 文字列 `123456789` の CRC32 は 0xCBF43926。

起動時に次のどれかに当てはまれば、キーマップの Flash の内容は無効とみなして初期キーマップを使う:

- マジックが違う
- フォーマットバージョンが未対応
- レイヤー数またはキー数が、そのファームの値と一致しない
- CRC32 が一致しない
- keycode 配列に、ファームが受け付けない値(未定義の keycode)が含まれる

`LOAD` でも同じ条件で無効と判断する(`LOAD` は `ERR` にせず、初期キーマップに戻す。§3)。

keycode の種類が増えても、配列の並びが変わらない限り、フォーマットバージョンは `1` のままとする。新しい種類の keycode を含むデータは、それに対応していない古いファームでは「未定義の keycode を含む」として無効になり、初期キーマップで起動する(データは壊れない)。

### 設定(マジック `TKC1`)

数値はリトルエンディアン。中身は、「名前=値」の文字(ASCII)を、1行ずつ並べたもの。

| オフセット | サイズ | 内容 |
|---|---|---|
| 0 | 4 | マジック `"TKC1"` |
| 4 | 1 | フォーマットバージョン(現在 `1`) |
| 5 | 2 | 文字の長さ(次の「文字」の部分のバイト数) |
| 7 | 文字の長さ | 文字。`名前=値\n` の繰り返し(例: `led=80\n`)。値が空のときは `tri0=\n` |
| 末尾 | 4 | 上記すべて(マジックから文字の終わりまで)の CRC32(キーマップと同じ計算) |

- 文字のあとの、使わない部分は、消去済みと同じ値(0xFF)にする。CRC32 は、使わない部分を含めない。
- 1行に入る名前は、重複しないこと。takoyaki8 は、全体で 1024 バイト、最大 32 個まで。入りきらないときは、`SAVE` が `ERR FLASH cfg too large` になる。
- 起動時に次のどれかに当てはまれば、設定の Flash の内容は無効とみなして、すべて初期値を使う:
  - 長さが足りない / マジックが違う / フォーマットバージョンが未対応
  - 文字の長さが範囲外 / CRC32 が一致しない
  - 行の形が不正(`=` がない、名前が空、改行がない)/ 個数が上限を超える
- 有効なときでも、値が、その名前で使えない(検査に通らない)ときは、その名前だけ初期値を使う。
- 知らない名前は、捨てずに持ち、`SAVE` のときも書き戻す(§4)。
- 名前を足しても、保存の形が変わらない限り、フォーマットバージョンは `1` のままとする。

書き込み中に電源が切れても CRC が合わなくなるだけなので、キーボードが使えなくなることはない(キーマップも設定も、初期値で起動する)。

## 6. 通信例

```
> INFO
< OK name=takoyaki8 proto=1 fw=0.5.0 keys=8 rows=2 cols=4 layers=4 cfg=1 lname=5 saved=1
> DUMP 0
< OK 0x5201 0x0A2B 0x082B 0x0151 0x0044 0x0150 0x014F 0x0152
> SET 0 0 0x001D
< OK
> GET 0 0
< OK 0x001D
> INFO
< OK name=takoyaki8 proto=1 fw=0.5.0 keys=8 rows=2 cols=4 layers=4 cfg=1 lname=5 saved=0
> SAVE
< OK
> SET 4 0 0x0004
< ERR RANGE layer 4 out of range
```

修飾キーとレイヤー切り替えの例(対応しているファームの場合):

```
> SET 0 0 0x00E1
< OK
> SET 0 1 0x0204
< OK
> SET 0 2 0x5221
< OK
> SET 0 3 0x5224
< ERR BADARG undefined keycode
```

`0x00E1` は左 Shift、`0x0204` は Shift+A、`0x5221` は MO(1)。`layers=4` のとき MO(4) は範囲外なので `ERR BADARG` になる。

次・前のレイヤー:

```
> SET 0 3 0x7E00
< OK
> SET 0 7 0x7E01
< OK
```

設定の例:

```
> CFG LIST
< OK lname0 lname1 lname2 lname3 led led_mode=layer|press|breathe|off lcolor0 lcolor1 lcolor2 lcolor3 oled rotate tri0
> CFG GET led
< OK 80
> CFG SET led 60
< OK
> CFG SET led_mode breathe
< OK
> CFG SET lname0 mac
< ERR BADARG bad value
> CFG SET lname0 DESK
< OK
> CFG SET tri0 1,2,3
< OK
> CFG GET tri0
< OK 1,2,3
> CFG SET rotate 45
< ERR BADARG bad value
> CFG SET foo 1
< ERR BADARG unknown name
> CFG SET led
< OK
> CFG GET led
< OK 80
> SAVE
< OK
```

`CFG SET led`(値なし)は、`led` を初期値(80)に戻す。`mac`(小文字)はレイヤー名に使えない。

## 7. 今後の検討事項

- DF / PDF / TT / OSL / LT / LM / MT など、ほかのレイヤー・修飾キー関連の keycode
- 設定を、まとめて初期値に戻す操作(いまは、`CFG SET <名前>` を名前ごとに送る。`RESET` は設定を戻さない)
- トライレイヤーの2つ目以降(`tri1` …)
- 効果の細かい設定(`led_speed` など)。キーが多い機種での、`press` の光る LED の位置
- 候補つきの設定を増やす(例: `rotate` の4つの向き。いまは、ツールが知っている)
- ロータリーエンコーダなど、キーと LED・OLED 以外の設定
- 複数ファーム間でのプロトコルバージョン互換の扱い。`proto` は、互換が切れる変更が出たときに、まとめて上げる
